# OPA — Operating Agent

> **Your personal operating system for work, learning, applications, projects, and execution.**

OPA is an AI-powered **personal operating agent** designed to turn scattered goals, opportunities, projects, academic work, applications, and daily tasks into one intelligent workspace.

Instead of using separate tools for planning, applications, outreach, projects, notes, and AI assistance, OPA brings them together into a single operating layer — with **JARVIS**, a context-aware AI agent that can reason over your personal data and help you decide what to do next.

---

## ✦ What is OPA?

OPA stands for **Operating Agent**.

It is built around a simple idea:

> **Your tools should adapt to your goals — not the other way around.**

OPA combines:

* 🧠 AI-powered personal assistance
* 📅 Daily planning and execution
* 🎯 Opportunities and applications
* 📬 Outreach management
* 🚀 Project tracking
* 🎓 Academic planning
* 📄 Resume intelligence
* 🧩 Context-aware RAG
* 💬 JARVIS conversational interface
* 📊 Personal history and progress
* ⚡ Automated workflows

The goal is not to build another productivity dashboard.

The goal is to build a **personal operating system**.

# 🧠 RAG Architecture

OPA uses **Retrieval-Augmented Generation (RAG)** to give the AI access to relevant personal context.

OPA does **not** fine-tune a model on your personal information.

Instead:

```text
Personal Data
     │
     ▼
Document Chunking
     │
     ▼
Embeddings
     │
     ▼
Vector-like document index
     │
     ▼
Relevant Context Retrieval
     │
     ▼
LLM
     │
     ▼
Grounded Response
```

## Indexed information

The RAG layer can index:

* Resume
* Projects
* Weak areas
* Daily reflections
* Sent emails
* Cover letters

Every relevant write operation can update the searchable context.

| Daily Plan           | Reflections, weak areas, project notes              |
| Opportunity Matching | Resume evidence, projects, previous cover letters   |
| Professor Outreach   | Relevant projects and previous successful outreach  |

---

## Embedding Model

The default embedding model is:

```text
BAAI/bge-small-en-v1.5
```

OPA uses `fastembed` for local embeddings.

A fallback hashed bag-of-words embedder is also available.

Configure it with:

```bash
RAG_EMBEDDER=auto
```

or:

```bash
RAG_EMBEDDER=fastembed
```

or:

```bash
RAG_EMBEDDER=hash
```

After changing the embedding strategy, rebuild the index:

```http
POST /v1/rag/reindex
```

# Frontend


# Backend

Move into the backend:

```bash
cd backend
```

Create a virtual environment:

```bash
python -m venv .venv
```

Activate it.

### Windows

```bash
.venv\Scripts\activate
```

### macOS / Linux

```bash
source .venv/bin/activate
```

Install dependencies:

```bash
pip install -r requirements.txt
```

# 🔐 Environment Variables

Create a `.env` file based on:

```text
backend/.env.example
```

At minimum, configure your Groq API key:

```env
GROQ_API_KEY=your_groq_api_key
```

For PostgreSQL:

```env
DATABASE_URL=your_postgres_connection_string
```

For RAG:

```env
RAG_EMBEDDER=auto
```

Never commit `.env` files or private API credentials to GitHub.

# 🧩 Database

OPA supports:

* Local development
* Prototyping

Default database:

```text
./opa.db
```

### PostgreSQL

Recommended for production deployments.

Configure:

```env
DATABASE_URL=postgresql://...
```

The backend is designed to work with PostgreSQL without requiring `pgvector`; similarity retrieval can be performed in Python.

---

# 💾 Persistence

If SQLite is used in production, make sure the deployment environment provides a persistent disk.

Without persistent storage:

```text
Application restart
       ↓
Ephemeral filesystem
       ↓
SQLite database may disappear
```

For production, use either:

```text
Persistent SQLite volume
```

or:

```text
Managed PostgreSQL
```

Possible PostgreSQL providers include:

* Neon
* Supabase
* Managed PostgreSQL from your deployment provider

The frontend and backend are currently designed as separate deployable pieces.



The frontend should use the backend URL for API requests rather than assuming the backend is running on localhost.

# 🧠 AI Design Philosophy

OPA follows a simple principle:

> **AI should augment your decisions, not silently make them.**

The system is designed to separate:

### Context

What OPA knows.

### Reasoning

What the AI determines from that context.

### Action

What should happen next.

### Approval

What the user actually allows.

Conceptually:

```text
Context
   ↓
Reasoning
   ↓
Recommendation / Draft
   ↓
Human Review
   ↓
Action
```

This is particularly important for actions such as:

* Sending emails
* Applying to opportunities
* Contacting people
* Updating important information
* Executing external workflows
